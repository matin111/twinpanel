# TwinPanel 1.1.25-rc.1 — Panel API stability canary

**Scope:** API auth/read transaction lifecycle and monitoring only. This is a
release candidate, not a published stable customer update.

## Fixed
- Avoid pinning a PostgreSQL `twinpanel-http` request-pool connection across
  slow route handlers after successful user/reseller authentication.
- End read-only auth transactions immediately, retaining identity fields with
  `expire_on_commit=False`.
- Add regression tests to the existing API CI gate.

## Production investigation (2026-11-26)
- Pre-hotfix: all 32 HTTP pool slots were repeatedly occupied by
  `idle in transaction` sessions and the API logged SQLAlchemy QueuePool
  10-second timeouts, surfacing as HTTP 500 across admin/reseller routes.
- Emergency narrow hotfix applied with file backup and rollback path on the
  controller; following samples showed fewer stuck HTTP transactions and no
  new QueuePool errors, but endpoint latency and 499s remained nonzero.
- A controlled API service restart alone did **not** solve the incident.

## Safe release gates before stable promotion
1. Full API build + preview validation pass for this source commit.
2. Canary HTTP p95 latency and PostgreSQL request-pool occupancy under
   realistic subscriber/reseller load, not just healthy systemd status.
3. Quota event counts and exact per-user attribution remain unchanged.
4. Verify login, reseller dashboard, subscriptions and checkout before/after.
5. Pre-update backup, SHA256 validation, monitored update + rollback.

## Explicitly not part of this release
- Draft Xray revoke fix #2819 (requires node canary).
- Draft canonical quota identity guard #2817 (requires account migration audit).
- WireGuard/AmneziaWG/Sudoku remaining failed revocations (#2818).
- No new protocol counter values or user balance migrations.
